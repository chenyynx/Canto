## 一、项目背景（这个仓库是什么）

### 1.1 Hako 是什么

Hako 是一个面向 Apple 全平台（iPhone / iPad / Mac / Apple TV）的**原生规则代理客户端**（Clash 类），GPL-3.0 开源，已上架 App Store。由三个独立仓库组成：

| 仓库 | 语言 | 职责 |
|---|---|---|
| `Hako` | Go | 代理内核（协议、分流、DNS、TUN），经 gomobile 编译成 `Hako.xcframework` |
| `Hako-Adapter` | Swift | Apple Network Extension 桥接层（包转发、provider 生命周期） |
| `Hako-Client` | Swift | 四平台 App + 扩展 + 共享 UI/配置库 |

三个仓库的依赖通过 `Dependencies.lock.json` 精确钉住 commit。我们已把三个仓库都镜像到自有 GitHub 账号下做二次开发（独立仓库，非 fork）。

### 1.2 已探明的关键代码事实（iOS 侧）

1. **代理内核只跑在 Network Extension（packet-tunnel-provider）进程里**，主 App 不含内核。
2. **内核已自带完整的 Clash 控制 API**（节点列表/切换/延迟测试、连接列表/断开、出站模式切换、DNS 查询、provider 更新、流量/内存/日志实时流），但在 iOS 上仅以 **App Group 容器内的 Unix socket（`clash.sock`，0600 权限）** 暴露，**不开 TCP 端口**。
3. **主 App 一进后台就主动断开内核连接**（应用自身代码行为），因此控制面不能挂主 App 进程。
4. **Extension 进程存活 = 隧道（VPN）存活**。隧道开着则常驻，关则进程消失。
5. 代码里已有一个**生产可用的进程外控制面原型**：`WidgetMailboxService`（小组件用，Darwin 通知 + App Group 文件邮箱 + 直接驱动内核），目前只支持 3 个命令；以及 `ConnectHakoIntent` 等 App Intent（可在 App 不在前台时拉起/断开隧道、切模式）。

## 二、需求（我们要做什么）

### 2.1 一句话

**让一个 AI agent 全权管理 Hako App 的一切**——订阅、节点、分组、规则、出站模式、VPN 开关，全部由 agent 决定和操作，用户日常不用打开 App 点任何东西。

### 2.2 关键约束（这些已和用户确认，不可妥协）

1. **远程场景为主**：agent 在用户自己的 Mac / 云服务器上运行（如 Claude Code、Cursor、自建 agent），手机上的 Hako 被它远程管理。同设备本地 agent 只是次要场景。
2. **给第三方用户用**：这是开放能力，不是绑定某家服务器。**App 里不预置任何 agent 地址**，用户自己连接自己的 agent。
3. **首次打开 App 就能连上 agent**，不需要先开 VPN。
4. **agent 端形态 = MCP server**（已定）：不造新的专属客户端程序，而是一个 MCP server，接入用户已有的 CC / Claude Code / Cursor 等 agent。
5. **用户心智模型**：用户只需理解一件事——「用手机扫一下电脑上那个码」。

### 2.3 用户的理想体验（最终态）

```
用户：装 App → 扫一次码连上自己的 agent
       → 之后订阅、节点、规则、VPN 全权由 agent 维护，用户零操作
```

## 三、技术方案已确定的部分（已论证，不要推翻，只需在此基础上细化）

1. **双连接架构**：
   - **App 连接器**（主 App 进程内）：App 启动即连 agent，负责注册配对、订阅管理、配置编辑、拉起 VPN。不依赖隧道。后台保活靠静默推送（content-available）+ 命令挂起队列。
   - **Extension 连接器**（Network Extension 进程内）：隧道开着时连 agent，负责内核级操作（切节点、测延迟、切模式、断连接）。由按需连接（On-Demand）兜底自动恢复。
2. **控制面必须挂 Extension 进程**（理由见 1.2-3：App 后台主动断连）。内核级操作的执行器是 Extension 里的 Go 内核。
3. **手机/Extension 主动出站连 agent**（WebSocket），agent 端被动接收——解决 NAT 问题。
4. **配对三路接入**：扫码（主推）/ 粘贴 `hako://pair?...` 口令 / 局域网 Bonjour 自动发现。
5. **App 侧 UI 已定型**：首页新增「Agent」卡片（与现有「出站模式/代理/规则」卡片同体系），整卡可点进二级页（扫码/口令/发现三路），另有设置页管理连接。文案已对齐现有设计风格。

## 四、iOS 硬边界（必须接受，写方案时绕不开）

1. **「允许添加 VPN 配置」系统弹窗必须人手点一次**——Apple 强制，无任何 API 可绕过。
2. **装完必须首次打开一次 App**。
3. **隧道关 = Extension 进程不存在 = 内核级操作不可用**（App 层操作仍可用；由按需连接自动恢复隧道）。
4. 构建需 macOS + Xcode 27 + Go 1.26.6；我们已配置 GitHub Actions macOS runner 做免签名编译验证，**开发反馈链已打通**（iSH 上改代码 → push → CI 编译验证）。

## 五、需要你（外部 AI）产出的东西

产出一份**产品级实施方案**，要求：

1. **配对手册**：token 交换、信任模型、设备列表、重连退避、多设备管理、断连恢复——具体到协议报文格式与状态机。
2. **MCP server 规格**：暴露哪些工具（list_nodes / switch_node / set_mode / manage_subscription / vpn_control / health_check 等）、每个工具的参数与返回、错误语义、幂等性。
3. **双连接器的消息协议**：App 连接器与 Extension 连接器各自的命令集、结果回传、事件推送（状态变化）、心跳与重连、命令冲突时的仲裁。
4. **分期路线图**：P0-P5，每期交付物 + 验收标准 + 依赖关系，特别注明哪些期需要 iOS 构建（受 GitHub Actions 限制，只做免签名编译验证，不真机分发）。
5. **风险清单**：iOS 生命周期（App 被挂起、Extension 被内存上限杀、静默推送延迟）、安全（配对鉴权、token 存储、同 App Group 内无鉴权 mailbox 的既有风险）、上游同步冲突。

## 七、当前卡在哪（最需要外部视角的点）

1. **配对协议**的最小完备设计——怎么做到既安全（防止别人乱连）又极简（小白只扫一次码）。
2. **App 连接器与 Extension 连接器的职责边界**——同一个 agent 同时面对两个「手机端进程」，命令路由、状态合并、冲突处理怎么设计才不混乱。
3. **隧道关闭期间的降级语义**——agent 能做什么、不能做什么，如何向用户和 agent 双方都清楚表达。
4. **产品化**：这是一个要给别人用的开源功能，文档、引导文案、设置项命名、错误提示都需要产品级打磨。
